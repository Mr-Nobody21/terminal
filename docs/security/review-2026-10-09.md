# Security review — 2026-10-09

Local source review and regression testing of the Fastify/PostgreSQL backend and shared web UI. This is not an independent penetration test or a claim that the application is ready for public production use. No external systems were attacked or scanned.

## OTP scope

The user requested the default code spoken as “9 zero 4 five 3 zero”, interpreted as **904530**. Login and registration now require a separate verification step before a session is issued. The shared fixed code is a development demonstration, **not a genuine independent second factor** and not a rotating one-time password. The five-minute challenge/token is single use; the demonstration code itself is reusable across challenges. `NODE_ENV=production` fails startup until a real second-factor provider is implemented. There is no setting to silently disable verification or permit the fixed code in production. No code is displayed by the UI or returned by the API.

## Findings and changes

| Finding | Severity / disposition | Change and evidence |
| --- | --- | --- |
| Password verification immediately granted full access | High, fixed for the requested verification workflow | Registration/login issue a random HttpOnly challenge cookie. Only `/auth/verify-otp` creates a verified session. Legacy session rows without verification are rejected after migration 004. |
| IP-only auth limits could be bypassed with multiple IPs or process restarts | High, mitigated | PostgreSQL atomic per-account and per-IP counters; eight password attempts/account/15 minutes, shared across service instances. OTP row locks enforce five guesses/challenge, expiry and replay protection. |
| Expensive password jobs could queue without bounds | High, mitigated | Four concurrent scrypt jobs/process; excess requests fail with 429 and Retry-After. Credentials limited to 12–128 characters; auth bodies 4 KB. |
| Existing scrypt work factor was below the selected current baseline | Medium, fixed with backward compatibility | New `scrypt-v2` hashes use `N=32768,r=8,p=3`, random 16-byte salt, 64-byte output. v1 verifies using original parameters and conditionally upgrades after a correct password without changing account IDs/auth versions. |
| Long sessions had no idle timeout or account session cap | Medium, mitigated | 30-minute inactivity limit, seven-day default absolute expiry, maximum five verified sessions/account, token rotation, password-change revocation of sessions and pending challenges. Auth-version checks invalidate stale password challenges. |
| Unbounded aggregate requests and storage consumption | High, mitigated with application limits | Aggregate 300 requests/IP/minute plus route limits; PNG/JPEG up to 5 MB and 32 MP, header dimensions inspected without decoding; 50 MB/500 uploaded assets and 100 project snapshots/account; advisory locks serialize quota decisions. These ceilings are not a substitute for infrastructure monitoring. |
| Security headers, audit trail and retention were incomplete | Medium, mitigated | CSP/frame/referrer/nosniff/permissions headers; UI preview headers and static-host `_headers` template. Auth events persist without passwords, OTPs or token values. IP digests are pseudonymous, not anonymous. Thirty-day event retention with bounded maintenance deletes. |
| Slow requests and database operations could occupy resources indefinitely | Medium, mitigated | HTTP request/connection/keepalive limits, DB statement and idle-transaction limits, 20-second browser API timeout/cancellation, explicit client cooldown from Retry-After. No automatic credential retries. |
| Repeated asset reads/writes incurred unnecessary work | Optimization | Public catalog uses a 60-second process-local cache with one in-flight load; duplicate private uploads reuse existing asset/blob IDs instead of rewriting bytes. |

## Implemented limits

| Control | Limit |
| --- | --- |
| Aggregate HTTP | 300/IP/minute, bounded in-memory cache; runs before CORS preflight handling |
| Register/login/password routes | 10/IP/route per 15 minutes |
| Registration shared IP counter | 5/hour |
| Password shared IP counter | 30/15 minutes |
| Password shared account counter | 8/15 minutes; reset only on successful OTP verification |
| OTP route / shared IP counter | 20/IP/15 minutes / 30/IP/15 minutes |
| OTP challenge | 5 minutes, 5 valid-format guesses, replacement invalidates prior token |
| Upload / project-save routes | 20/IP/minute / 60/IP/minute |
| Hashing | 4 in-flight jobs/process; no unbounded waiting queue |
| Request body | 10 MB general, 6.7 MB upload envelope, 4 KB auth, 1 KB OTP/logout |
| Uploaded asset budget | 50,000,000 bytes and 500 unique files/account |
| Project budget | 100 snapshots/account; each request remains bounded by the general body limit |
| HTTP / client deadlines | 15s request, 10s connection/keepalive; 100 requests/socket; 20s client timeout |
| Database deadlines | 10s statement, 15s idle transaction, 5s connect; pool maximum 10 |
| Cleanup | Once/minute; up to 1,000 expired rows/table per pass; event retention 30 days |

The normal Fastify rate-limit hook skips a second hook from the same plugin once it has run. The aggregate limit therefore uses `createRateLimit`, separately from route hooks. Tests assert both route limits and a shared limit across different endpoints to prevent regression.

## Existing controls checked

SQL uses parameterized values; generated schema names in tests are trusted UUID-derived identifiers. Project/drawing JSON is strictly validated before SQL writes. User ownership is checked on private assets/projects; cross-user IDs return 404. API keys remain browser-memory-only and cannot pass canonical schemas. Source SVGs are reviewed seed assets, not user-uploadable files. Exporters escape text and attribute values; inline sequence SVG derives only from validated shapes and escaped labels. Auth cookies are HttpOnly and SameSite=Lax by default; Secure is required for cross-site mode. Mutations require custom CSRF header and allowed Origin when present; credentialed CORS has no wildcard or null origins. Proxy headers are not trusted.

No canonical project/drawing or pricing contract changed. Migration 004 adds backend-only verification, challenge, throttle and audit metadata. Existing projects/uploads/accounts remain; pre-OTP sessions require sign-in again. Existing password hashes upgrade on correct-password login.

## Residual issues / deployment gates

- Replace the fixed code with enrolled TOTP/passkeys or a real delivery provider, including secure recovery, before enabling production. Google sign-in remains disabled.
- Email ownership verification, account recovery/password-reset delivery and account-registration enumeration resistance are not complete. Registration still returns 409 for an existing email; timing is not claimed to be perfectly uniform, especially while upgrading legacy password hashes.
- Global/route IP limits are process local; shared database auth counters persist across instances. A public multi-instance service also needs edge/network DDoS protection and coordinated global limits. No Redis or paid edge service was provisioned.
- Reverse proxy trust is disabled. Configure only known proxy hops before deployment; blindly trusting X-Forwarded-For permits IP-limit bypass. Behind a proxy without configuration, peer-IP limits may apply to all users together.
- UI CSP allows HTTP/HTTPS connections for user-selected BYOK endpoints and inline styles needed by React Flow. It blocks inline scripts/eval and embedding, but cannot prevent a compromised authorized script from calling an allowed AI endpoint. Static hosts must actually apply `_headers` or equivalent server headers; Vite dev intentionally retains HMR compatibility. Native Tauri CSP remains managed by platform configuration and is not replaced with web headers.
- Asset checks inspect type/size/dimensions; they are not a malware scanner or full image decoder. Use updated browsers and trusted reviewed SVG sources. Local IndexedDB recovery is logically account scoped, not encrypted against someone with browser/device access.
- Quotas cap uploaded blobs and snapshot counts, not all PostgreSQL physical usage. Snapshot JSON retains embedded image recovery caches, and schema/index/audit overhead still exists. Monitor database/disk usage and apply least-privilege database roles, TLS, secrets management, backups and restore drills before deployment.
- No production deployment or desktop rebuild/auth verification was performed. Large ELK/report frontend chunks remain; unrelated domain refactoring was avoided.
