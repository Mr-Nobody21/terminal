# Browser AI and requirement planning

AI is optional. Manual edits, deterministic pricing, storage, and export work without credentials or network access. Only explicit submission sends requirement text, clarification answers, assumptions, provider/region, and the service catalog to the configured endpoint. Provider calls may incur charges. Keys exist only in an adapter closure and UI memory; preferences explicitly serialize only provider, endpoint, and model.

Adapters issue browser-direct requests using documented [OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create), [Anthropic Messages](https://platform.claude.com/docs/en/api/messages), and [Gemini generateContent](https://ai.google.dev/api/generate-content) formats. API envelopes are separately validated. Model names are user configuration, not claims of account availability. A local OpenAI-compatible endpoint may use HTTP on localhost. Hosted endpoints require HTTPS; browser CORS failures are recoverable and do not create a proxy.

The complete Zod JSON schema is embedded in the instructions; OpenAI-compatible JSON mode and Gemini JSON MIME mode request structured JSON. Every result passes local strict Zod validation. Generated proposals additionally pass the complete project reference/provenance/provider checks. One repair request is permitted after invalid JSON or semantic validation; transport failures are never repaired or retried. Requests support timeout and cancellation. Error messages never include provider response bodies or credentials.

Extraction labels user/PRD facts, proposes visible inferred assumptions, and ranks at most eight clarification questions by criticality and architecture/cost impact. Critical unknowns need an answer or an explicitly linked user assumption before architecture generation. Existing references survive extraction. Lean and Recommended replace the prior architecture only after both have passed validation; failure leaves the original project intact. AI cannot provide coordinates, prices, or export XML. Unsupported services require the canonical unsupported flag/category and remain unpriced until manually replaced.

## BYOK service presets

AI settings include OpenRouter (`https://openrouter.ai/api/v1`), Groq (`https://api.groq.com/openai/v1`) and Custom OpenAI-compatible alongside the existing OpenAI, Anthropic, Gemini and local adapters. Presets use the documented [OpenRouter Chat Completions interface](https://openrouter.ai/docs/quickstart) and [Groq OpenAI compatibility](https://console.groq.com/docs/openai). Custom hosted endpoints require an HTTPS API base URL, a model ID and their own API key; local HTTP remains restricted to localhost. No provider SDK, backend or runtime dependency was added.

Select the service in AI settings, enter its model ID (OpenRouter uses the full `provider/model` identifier), and enter your key. Return to the workspace and submit extraction or generation. Changing the provider or API base URL clears the current key. Model/JSON-mode edits keep the key in memory. Keys are excluded from preferences and project exports and disappear on reload.

The JSON-mode checkbox requests `response_format: {type: 'json_object'}` for compatible services. OpenRouter also receives `provider.require_parameters: true` to avoid routing to providers that ignore required parameters, following its [provider parameter guidance](https://openrouter.ai/docs/guides/features/structured-outputs). For models without JSON mode, disable the checkbox; schema instructions, strict local Zod/semantic validation and the single repair bound remain in force. No routing fallback or network retry is added. Model IDs and availability are user-configured; no catalog fetch happens merely by selecting a service. Optional OpenRouter attribution headers are omitted, so the application does not supply a site/profile URL.

Provider/model/endpoint and the optional JSON-mode preference are persisted separately from projects. Previous four-provider preferences remain valid without a migration; no canonical project-schema change occurs. New providers use the same cancellation, timeout, CORS, validation and unchanged-project-on-failure behavior. Credit exhaustion and unsupported models/JSON-mode requests produce recoverable messages without revealing response bodies. Live provider connectivity depends on CORS and account/model access; validation uses mocks and does not incur provider charges.
